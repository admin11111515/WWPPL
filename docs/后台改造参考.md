## 1. Flowbite Astro Admin（唯一同技术栈的，结构可以直接照）

我把它的**设置页**和**产品列表页**源码拉下来逐块看过，实测结构：

### 设置页（对应我们的「站点信息」「站点外观」）
- 页面顶部是「面包屑 + H1 标题」，**下面全是卡片**：一个设置区块 = 一张卡片
  （自带边框 + 圆角 + 阴影），卡片之间靠外边距分开，**不靠分隔线**
- 卡片**内部**的列表项之间才用 `divide-y` 细线分隔
- 表单字段：**标签在上、控件在下**，外面套 `grid-cols-6`，字段用 `col-span-6 sm:col-span-3`
  → 宽屏一行两个字段（**我们上一版的两列就是这个做法**）
- 开关类区块：`flex items-center justify-between py-4` + 左说明右开关（**我们已经是这个**）
- **每个区块底部各自一个 «Save all»**，自适应宽、靠左，不是通栏

### 产品列表（对应我们的「文章管理」）
- 列表是**原生 `<table>`**，不是 div 行
- 每行第一格是名称（主文本）+ **分类作为名称下方的副文本**，分类不单独占一列
- 操作按钮是**图标 + 文字**：铅笔（编辑）、垃圾桶（删除），图标 `w-4 h-4 mr-2`（16px）
- 工具栏：搜索框（无按钮）+ 刷新（图标+文字）+ 新建（**加号图标 + 文字**）
- 新建/编辑/删除都走**右侧抽屉（Drawer）**，不跳页、不弹 alert
- 列表底部有分页组件

**抄什么**：抽屉式编辑、每区块一个保存、表格行"主+副"两行结构、按钮里图标用 16px
**别抄**：它停在 2023-12（Astro 3 / Tailwind v3 时代），整套搬会踩版本坑

## 2. shadcn-admin（★15k，抄"现代后台的布局语言"）

它最好看的不是配色，是一整套约定：

- 左侧**可折叠侧边栏** + 顶部 header（面包屑 / 全局搜索 / 主题切换 / 用户菜单）
- **命令面板（⌘K）**：键盘直达任意页面和常用动作
- 数据表：排序、筛选、分页、行选择，**行操作收进「⋯」菜单**
- 骨架屏（skeleton）加载态、规范的空状态

**抄什么**：
1. **行操作收进「⋯」菜单** —— 我们文章行现在平铺 3 个按钮，窄栏里标题被挤到 160px；
   收成 1 个「⋯」+ 弹层，标题能恢复全长。**这一条最该做。**
2. **⌘K 命令面板** —— 八个后台页 + 「新建文章 / 写说说」，纯前端能做，不用后端
3. **骨架屏** —— 现在列表加载是「正在加载…」转圈
**别抄**：侧边栏导航。站长明确要博客那条导航栏，后台不要另立一条。

## 3. tabler（★41k，当"完备度清单"用）

纯 HTML/CSS 的后台成套件，今天还在更新。价值不在抄代码，在于它把**一个后台该有的状态**
全做齐了：表格的每列类型、表单校验态、空态、Toast、Badge、进度条、错误页……

**用法**：当作标尺 —— 我们后台缺哪个状态，去它那儿看现成的长什么样。
**别抄**：它建在 Bootstrap 上，引进来会和我们的 Tailwind v4 令牌打架。

## 4. AdminLTE（★45k）

经典老牌，信息密度高。**统计卡 / 小部件**那块排得最成熟 —— 我们首页那四格统计
（文章/说说/笔记本/最近提交）+ 九张入口卡，可以对着它调比例。
**别看**它的配色和图标风格，是十年前的味道。

---

## 5. next-shadcn-admin-dashboard（★3k，抄"预设"思路）

亮点是**主题预设**和**布局宽度可切换**：配色不是给一个色相数字，而是几套命名预设
（Tangerine、Neo Brutalism、Soft Pop…）一键切。

**抄什么**：我们的 `/admin/appearance` 现在是一个色相数字框 + 8 个色块。
可以升级成"命名预设 + 自定义"，比调数字友好得多。

## 第四批（2026-10-03）：**撤掉顶部博客导航栏 + 内容加宽 1180**

站长这两句要求是分开的：**「内容宽度应该再宽一点」**、**「后台管理页面中，不需要顶部博客导航栏了」**。
两条一起做完之后，后台顶部的形态是**一条顶栏都没有** —— 只剩「一行页头 + 侧栏 + 内容」三块。

### 为什么撤导航栏不是"删一个组件"

博客那条 `<Navbar />` 在后台不只是一排链接，它还**承着三个动作**，删之前得先给每个找好接手的地方
（少一个就会变成"找不到按钮"，我们在这上面栽过一次）：

| 它原来管的事 | 后台里还有没有用 | 改由谁接 |
|---|---|---|
| 切主题（亮 / 暗 / 跟随系统） | **有**，后台也要能切 | 页头右侧的 `LightDarkSwitch` |
| 回前台 | 有 | 侧栏底部「看前台」（新标签打开） |
| 回后台首页 / 换功能 | 有 | 侧栏那几组入口 + 页头左「← 后台首页」面包屑 |
| 音乐 / 背景播放 / 显示设置 / 搜索 | **没有**，全是前台功能 | 撤掉，本来就是噪音 |

⚠️ **撤掉后主题开关的开合要自己接一次**：`#scheme-switch` 的 toggle 原来由
`Navbar.astro` 里的 `loadButtonScript()` 管，那个脚本随导航栏一起不再加载，
所以 `AdminTopBar.astro` 尾部补了一段自己接的 `<script is:inline>`。
**以后谁再动页头，别把这段删了**（删了主题面板点不开，还不报错）。

### 布局的连带改动（只看一眼改宽度一定会溢出）

| 改了什么 | 连带要改什么 | 不改会怎样 |
|---|---|---|
| 侧栏 `grid-row` 从 `2 / span 2` 改成 `1 / span 2`、`top` 从 `4.75rem` 归零 | 4.75rem 原来是对齐那条 72px 的 sticky 导航栏；页头现在成了第一行，还是那个值就会在侧栏顶上留一段空白 | 侧栏往下缩一段、随页面滚动 |
| `--admin-content-max` 960 → **1180** | 必须同时摘掉 `.container` 那条 `@media (min-width:1280px){ width:92vw }` | 92vw 比网格第 2 列（视口 − 侧栏 216px）宽 → 顶出轨道、横向滚动条 |

**1180 这个数是量出来的**：撤掉那条 72px 横向导航栏后，宽屏中间正好空出这块；
1180 ≈ 一行 70 个汉字，编辑器正文不至于长到读一行要转头。实测 1280 / 1440 / 1920 / 390 四档
都无横向溢出（390 那档靠 CDP 强制视口，headless 的最小窗宽量不到真窄屏）。

### 仍然成立的红线

- 页头**没有底色、不吸顶**，就是内容区宽度里的一行，不是另开一条横贯全宽的条
  （这条过第三版就被否过一次：「这一栏完全没有必要保留」）
- **前台博客页面完全不受影响** —— 改完回前台跑了一遍对照：博客导航栏与主题开关照旧，6 个菜单一个不少
- 只抄尺寸与结构，**不引任何第三方包**

## 第五批（2026-10-04）：**「文章显示不全」其实不是宽度问题**

站长说「内容区再宽一点，不然像『文章』这种会显示不全」。先量后改，结论跟直觉相反：

| 实测（1366 / 1440 / 1920 三档） | 结果 |
|---|---|
| `.post-title` 宽度 | **恒为 160px**，与窗口宽度无关 |
| 最长那条标题「Astro Content Collections，迁移完我才敢乱改 frontmatter」 | 溢出 **185px**，永远显示成「Astro Content Colle…」 |
| 页面横向溢出 | 0（所以不是"装不下"，是**被自己的规则切掉**） |

**病灶有两处，缺一不可**：

1. `/admin/posts/` 左栏（`.layout-grid` 第一列）是**写死的 400px**；
2. `.post-title` 是「单行 + `text-overflow: ellipsis`」。

**只调 `--admin-content-max` 一点用都没有** —— 标题拿到的宽度由列宽决定，不由窗口决定。
改法是两边一起动：

- `.post-title` 允许**两行**（`-webkit-line-clamp: 2` + `overflow-wrap: anywhere`）——
  长标题读得完，短标题仍只占一行
- 文章页左栏 400 → **480px**
- 文章页 `--admin-content-max` 1100 → **1320px**；全局 1180 → **1280px**

验收：58 条标题**横向 0 条、纵向 0 条**被切；八个后台页全扫一遍（`_gen/_后台列表截断普查.mjs`）
再没有可见文字被切；1366/1440/1920 三档横向溢出均为 0。

⚠️ 普查里剩下的「纵切 78px `.container`」「横切 4px `.post-list-scroll`」**不是问题**：
前者是容器自身的滚动尺寸、后者是滚动条内边距那套固定写法，别照着"修"。

**教训**：用户说「显示不全」时，先量到底是**容器不够宽**还是**内容被规则切掉**。
这次如果照着"加宽"改，改到 2000px 也还是那个省略号。

### 第十批（2026-10-05）：同一张图不再传第二份（**按内容**去重）

站长第二次报：**「怎么还是在图片库中存在着我拖动已经存在的图片会导致复制并上传的问题存在呢？」**

⚠️ 上一批修的是**另一条路**（拖**页面里**的图），那条没错、也没白做；这次是**第二条路**，
两条加起来才是完整的。教训记在最下面。

| 真因 | 修法 |
|---|---|
| **去重只比文件名**：仓库里的图都是上传时生成的时间戳名（`20261005-…webp`），本地那张叫「封面.jpg」—— 名字永远对不上，于是"拖一张已经传过的图"就又多出一份 | **按内容判重**：算字节的 git blob 校验值（`SHA1("blob " + 长度 + "\0" + 字节)`）和仓库里每张图的 `sha` 直接比。**量两份**：原始文件一份、压缩后的字节一份，任一份撞上就认定"已经有了"，不传，并把那一张闪一下 + 复制它的 Markdown |
| 压缩会改字节，于是"同一张图再拖一次"的校验值对不上，去重形同虚设 | **压缩幂等**：已经压过的小 webp（≤500KB）不再压第二次 —— 顺带也别再削一刀画质 |
| **预览浮层的大图**能拖起来：它是点开预览时才插进 DOM 的，不在 `#media-list` 里，上一轮那条禁拖监听管不到（实测 `draggable` 是空的、`dragstart` 也没人拦） | 禁拖从"缩略图那一片"提到**整个文档**：页面里的 `img` / `a` 一律不让起拖，以后新加的图自动跟着走 |
| 被拦下的 `dragstart` 仍会置 `internalDrag = true`，而拖根本没启动、永远等不到 `dragend` → 标志卡住 → 之后**从系统拖文件进来传不了**（"该传的传不了"） | 拦下的那次直接 `return`，不置标志 |

**尺子只有一把**：算法在 `public/js/admin-github.js` 的 `WBGitHub.blobShaOf`
（后台页脚本都是 `is:inline`，**没法 import 模块**，共用工具只能挂到这个全局对象上）。
图片库与文章编辑器两页都用同一把 —— 编辑器那条路也有同一个病根，一并修了。

**顺带修了本地预览器**（不修的话这条在本地根本验不出来）：
- `gitBlobSha` 传 Buffer 时不能再当字符串按 utf8 转一次（二进制会被解码坏掉）；
- 目录清单里图片的 `sha` 必须用**真实字节**算（原来 `readRepoFile` 只认 `src/` 下的文本，
  `public/images/**` 一律读不到 → sha 成了"空内容"那个值 `e69de29…`）；
- 仓库里没有、但预览里刚传过图的目录也要能列出来（新建文章传图那条路）。

**教训（写给自己）**：一个"重复上传"的抱怨背后可能有**好几条独立的路**。上次修完一条就收工，
于是站长第二次报 —— **修完要按"用户会怎么操作"把同源的路径都走一遍**（页面里的图 / 系统里的图 /
预览浮层的图 / 编辑器里的图），别只堵住当时看到的那一处。

### 第十一批（2026-10-05）：文章编辑器「可视区太小」

站长原话：**「文章板块我想写篇文章，或者说修改文章，发现这可视区实在是太小了」**。

先量，别猜。同一个 `textarea#content-input`，三档屏宽：

| 视口 | 内容容器 | 占屏 | 正文输入区 | 一行几个汉字 |
|---|---|---|---|---|
| 1440 | 1220 | 85% | **292 × 520** | **20** |
| 1920 | 1280 | 67% | **322 × 520** | **23** |
| 2560 | 1280 | **50%** | **322 × 520** | **23** |

三个病根，**单改容器宽度治不了 292px 的输入区**，得一起动：

| 真因 | 修法 |
|---|---|
| **页面里写的容器上限是死代码**：七个后台页各写了一条 `#admin-main { --admin-content-max: … }`，而 `admin.css` 被 `import` 后打包成外链 `<link>`、Astro 把它放在 `<head>` **最后**（所有内联 `<style>` 之后）→ 同特异性下后写者胜，全被压掉。表现：文章页写了"1320"两年从没生效，1920/2560 屏上容器**永远停在 1280** | 变量改声明在 `.container` **自己身上**（`#admin-main > .container`，多一个类 = 特异性更高，且元素上声明的值本来就压过继承来的）。文章页一档 **1760**（只留一档：内容区实际宽 = 视口 − 侧栏 216px，要到 1976px 以上的屏才顶到上限，分两档没意义） |
| 编辑器**默认"左右各一半"**：编辑窗格只有卡片宽度的一半，480px 的列表栏再吃掉一块 → 这就是 292px 的来源 | 窗格改**三态**：编辑 / 分栏 / 预览，**默认「编辑」**（整行给 Markdown）。分栏保留（两个窗格各一半），点过就记在本机。窄屏没有"分栏"这一档，那颗按钮自己隐掉 |
| 编辑区高度**写死 520px**，1080p 上写完一段就得在半屏高的框里滚 | 跟着视口长：`min-height: max(560px, calc(100vh - 20rem))`。⚠️ 编辑与预览**必须用同一条算式** —— 它们同处一个网格行，一高一矮就会在矮的那个下面空出一截底色 |

**另外给了一个「隐藏列表」开关**（页头右侧，只在大屏出现）：480px 的列表是"找文章用的"，
真开始写就该让位；收起了按钮还在，一键放回来，不会把找文章的路堵死。状态同样记本机。

实测口径（`_gen/_文章页宽度改造核验.mjs`，58/58）：

| 视口 | 默认（编辑 + 有列表） | 收起列表 | 收起列表 + 分栏 |
|---|---|---|---|
| 1440 | 一遍 41 字（原 20） | 77 字 | 38 字 |
| 1920 | 76 字（原 23） | 111 字 | 55 字 |
| 2560 | 80 字（原 23，容器占屏 50% → 69%） | 115 字 | 57 字 |

编辑区高度三档都是 680（视口 1000 时）；三档 + 900px 窄屏**都没有横向溢出**；
刷新后「收起列表 + 窗格模式」都还在（写进 localStorage，且在 `<head>` 里提前恢复，
不会先按默认画一遍再跳）。前台 `/`、`/about/`、`/archive/`、`/music/` 在
375/768/1440/1920 下 16/16 无溢出（`_gen/_前台溢出复查.mjs`）。

**踩到的坑（这次的教训比改动值钱）**：
往 `admin.css` 那段注释里加字时**写早了收尾符** —— CSS 注释不嵌套，正文里出现一次
就当场收尾，下面 7 行整段掉到注释外变裸 CSS，`*/` 直接触发解析错误，把文件末尾
`#admin-main { --admin-content-max }` **整条吞掉**。表现极其迷惑：页面"看着有样式"、
不报错、构建也过，只是容器上限悄悄退回 `--page-width` = 96rem = **1536px**。
是核验脚本量出"容器 = 1536 而不是 1600"才揪出来的。
→ **改完注释先数一遍收尾符**（文件里 `/*` 与 `*/` 数量必须相等，
   注意 `/admin/*` 这种正文里的 `/*` 不配对，别被自己的扫描器骗了）。
