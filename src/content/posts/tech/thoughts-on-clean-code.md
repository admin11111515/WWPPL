我看了不少讲代码整洁的文章，观点差得挺远。把自己实际用下来的几条记一下，不追求优雅，追求半年后还能改。

起名这事我有个标准：读这一行的时候，要不要跳去定义看它是什么。要跳，说明名字没说清。`data`、`handle`、`temp` 这种，看名字啥都不知道。我现在的习惯是名字里带出"一组还是单个""原文还是处理后的"那种感觉，不是加类型前缀那种做法。

函数长度我不太信"不能超过二十行"这种死规矩。我的标准是：这个函数能不能一句话说清在干嘛。能说清，一百行也行，只要里面是直来直去的流程；说不清，十行也太长——那它干了不止一件事。行数只是症状，根子是"干了不止一件事"。

注释我只在这几种地方写。一种是"为什么这么做"：代码本身说了怎么做，说不清的是为什么——比如为什么这里要等 300 毫秒、为什么这个判断得放前面。一种是看着能删但删了会出事的代码，这种必须写一行，不然下个接手的人（包括半年后的我自己）一定手痒删掉。还有 TODO，但要写清啥时候能解决，不然就是永久临时方案。

错误处理这条我最较真。别吞错误——出错就返回一个默认值让它静默过，最危险，问题会在很远的地方炸，还找不到源头。能处理的就处理，处理不了就明明白白报出去。宁可失败得吵一点，也别安静地出错。

有回 code review，同事指着一段问我"你这注释是不是写多了"，我说"多总比半年后看不懂强"。这话是我自己说的，但真出过事：一个判断没写为什么，后来被人"优化"掉，线上挂了两小时。从那以后我宁可啰嗦。
