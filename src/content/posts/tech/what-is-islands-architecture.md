这个概念我第一次听也懵。用一个具体页面讲会清楚很多。

假设一个页面有三个部分：文章正文（纯文字）、一个点赞按钮、一个评论区。

## 传统单页应用的做法

整个页面都是 JavaScript 渲染的。用户打开网页，浏览器先下载一大坨脚本（可能几百 KB 到几 MB），执行，然后才把内容画出来。中间这段时间页面是白的。

问题在于：文章正文根本不需要 JavaScript，它就是一篇文章。但为了点赞按钮和评论区，整篇文章都被拉进了脚本世界。

## Islands 的做法

页面在构建时就生成了 HTML：正文就是 HTML，直接能看。

点赞按钮和评论区是两块"岛"。只有这两块会加载 JavaScript。而且可以分别指定：点赞按钮需要马上能点，就用"立即加载"；评论区在页面最下面，用户要滚下去才看到，就用"滚动到附近再加载"。

结果：首屏 HTML 一到就能读，JavaScript 只加载真正需要交互的那部分。

## 一个数字

我自己的博客改之前，首页要下 700 多 KB 脚本；改之后，因为大部分组件都标注了"不需要 JavaScript"，剩下的只有搜索和几个交互组件，脚本少了一大半。

## 什么算"岛"

判断标准很简单：**这块内容会不会因为用户操作而变化？**

- 会变 → 岛，需要 JavaScript
- 不会变 → 就是 HTML，别给它加载脚本

按这个标准过一遍，你会发现页面上真正需要交互的地方往往很少。侧边栏的卡片、页脚的链接、文章列表的标题——这些以前在单页应用里都在脚本里，其实一点都不需要。

## 什么时候不适合

后台管理系统这种几乎全是交互的页面，Islands 反而不如传统做法省事——反正整页都要交互，不如统一用一个框架。

它最适合的是「以内容为主、只有零星交互」的站点：博客、文档、官网、电商的产品页。
