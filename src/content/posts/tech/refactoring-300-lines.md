有个函数，三百多行，我三个月前写的。当时是"先能跑"的思路，一层层往里加，加到后来自己都懒得看。

这次花了一个下午重构，记一下过程。

## 先不改，先读

我做的第一件事是什么都不改，从第一行读到最后一行，在旁边写注释：这段在干什么。

读完发现它干了六件事：读文件、校验数据、清洗字段、按规则分组、调接口、写结果。

三百行里，真正复杂的只有"按规则分组"那一段，其他五段都是直来直去的流程。

## 拆

按这六件事拆成六个函数，主函数变成这样：

```js
async function run(input) {
	const raw = await readInput(input);
	const valid = validateRows(raw);
	const cleaned = cleanFields(valid);
	const groups = groupByRule(cleaned);
	await sendGroups(groups);
	writeResult(groups);
}
```

主函数从三百行变成六行，但这不是重点。重点是**现在每一步都能单独测**。

## 顺手改掉的三件事

**把魔数变成命名常量。** 原来散落着 `> 20`、`=== 3`、`slice(0, 5)` 这样的判断，看完不知道 20 是什么。命名之后代码自己会说话。

**把嵌套的 if 拉平。** 原来最多嵌了五层，最后一层的 else 根本不知道对应哪个 if。改成提前返回，最多两层。

**把错误信息写具体。** 原来出错就抛一句"数据异常"。现在会告诉你哪一行、哪个字段、期望什么。查问题的时候这一条最省时间。

## 拆完的收获

三百行变成四个文件，总共还是三百多行——行数没减少。

但改一个 bug 的时候完全不同了：以前要在三百行里翻，现在直接找对应那个函数，看完就改。而且因为每个函数职责单一，改 A 不太会影响 B。

## 我的判断

什么时候该重构？我的标准是：**当你"不敢改"的时候**。

如果每次动这段代码都要先在脑子里跑一遍全部逻辑，怕改坏别的地方，那不管代码多少行，都该重构了。
